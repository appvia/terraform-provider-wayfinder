# wayfinder_ai_skill (Data Source)

AISkill is markdown telling the assistant how to do one job — what the page a person is on is for, what to do and what to leave alone there, and which kinds of configuration a suggestion on it would be.

The assistant is told the name and description of every skill it can read, and the page a person is on can name the skill that covers it. The assistant reads a skill's body when it needs it, as the skill stands at that moment, so an edit applies from the next time a conversation reads it.

Wayfinder ships skills for its own pages, referenced as "wayfinder/NAME"; a tenant writes its own and references them by a bare name. A tenant's skill adds to the shipped ones and does not replace them: a tenant skill with the same name as a shipped one is a second, separate skill. Anyone signed in can read the shipped skills, e.g. with "wf get aiskills --scope system". A skill is held by the tenant, not by a workspace or an environment, and every AI user in the tenant can read it, so do not put anything in one that they should not see.

A skill is not an AIContext: a context is the standing background an agent starts with whatever it is doing, a skill is how to do the job the person came for.

<a id="nestedatt--mcps"></a>
### Nested Schema for `mcps`

Read-Only:

- `inputs` (Attributes List) Inputs are the values this agent calls the MCP with, for the inputs the MCP declares. They take precedence over the MCP's own, so one MCP serves many agents instead of a copy per agent, each pointed at a different account.

This is also how an agent avoids a hardcoded credential. A value may read the agent's own inputs, e.g. "${{ .Inputs.ddCredential }}", so the identity comes from whoever starts the conversation — one they hold at their own workspace or environment and are permitted to use — rather than one baked into the agent that the caller may have no access to.

Whoever supplies an identity is checked against their own grant: a literal named here is checked when the agent is saved, a value supplied by a conversation when that conversation starts, and the resolved credential again when the call is made, so a grant withdrawn in between stops working. (see [below for nested schema](#nestedatt--mcps--inputs))
- `mcp` (String) MCP is the scope-aware reference to the MCP server this binding exposes to the agent: "wayfinder/NAME" for one shipped with Wayfinder, a bare "NAME" for one of the tenant's own. A built-in agent may only reference "wayfinder/NAME".
- `tool_scope` (String) ToolScope selects whether the agent receives every tool the MCP server advertises ("all") or only the subset listed in tools ("selected"). An empty value is treated as "all".

- `all`: Exposes every tool the MCP server advertises to the bound agent. It is the default when ToolScope is unset.

- `selected`: Exposes only the tools named in the binding's Tools list to the bound agent.
- `tools` (List of String) Tools is the list of the server's tool names the agent may call. It applies only when toolScope is "selected", and must be empty when it is "all". A name the server no longer advertises is ignored.

### Nested Schema for `result_choice`

Read-Only:

- `badges` (Attributes List) Badges are labels shown on an option when a field of it is true, e.g. {"label": "Verified", "when": "verified"}. (see [below for nested schema](#nestedatt--result_choice--badges))
- `description` (String) Description is a paragraph shown for each option, e.g. "{description}".
- `facts` (Attributes List) Facts are labelled values shown for each option, e.g. {"label": "Downloads", "value": "{downloads}", "format": "number"}. A fact whose value is empty is left out. (see [below for nested schema](#nestedatt--result_choice--facts))
- `from` (Attributes) From names the command whose output the options are chosen from, e.g. {"command": "search-terraform-modules", "list": "candidates", "key": ["source"]}. Each option must match an entry the command returned, and is shown with that entry's fields added, so the facts the person sees come from the command rather than from the assistant. An option that matches nothing is refused. The templates below can then name the entry's fields as well as the option's; where both have a field, the option's is used. (see [below for nested schema](#nestedatt--result_choice--from))
- `items` (String) Items is where the options are in the result: the name of a list, or a path through objects to one with '.' between the names, e.g. "candidates" or "shortlist.modules". Each option is an object.
- `label` (String) Label is what the person reads for each option, e.g. "{source} {version}".
- `link` (String) Link is a web address the person can open for each option, e.g. "{sourceRepoURL}". It is shown only when every field it names came from the command's entry, with the same value on the option if the option has it too, as a key field does, and it is an http or https address. So an address the assistant wrote itself is never a link. It needs from.
- `message` (String) Message is what is sent for the person when they pick an option, as their next message, e.g. "Use {source} version {version}".
- `reason` (String) Reason is why the assistant offers the option, e.g. "{reason}".
- `recommended` (String) Recommended is where in the result the assistant names the option it recommends, as the value of the option's first from.key field, e.g. "recommended". The path is written as for items. That option is marked as recommended. It needs from.
- `subtitle` (String) Subtitle is a line shown under the title, e.g. "version {version} from {upstream}".
- `title` (String) Title is the heading each option is shown with, e.g. "{source}".
